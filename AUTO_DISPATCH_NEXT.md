# Следующий этап: системный автовызов и начало обслуживания

> Архитектурная заметка от 20 июля 2026 года. Изменения в коде ещё не реализованы.

## Зачем это нужно

Сейчас инициатива фактически принадлежит оператору: даже включённый автовызов запускается таймером в браузере оператора, после чего интерфейс вызывает существующий endpoint `/tickets/next`.

Это автоматизация интерфейса, а не системный диспетчер. Если вкладка закрылась, компьютер уснул или пропала сеть, таймер не выполнится. Сервер не владеет расписанием вызовов и не может гарантировать назначение следующего клиента.

Целевая формулировка процесса:

> Система автоматически назначает и вызывает следующего клиента для доступного онлайн-оператора. Оператор подтверждает фактическое начало обслуживания.

## Целевая модель талона

Жизненный цикл:

```text
waiting → called → serving → finished
             │         │
             ├─ повторный вызов
             ├─ не явился / отменён
             └─ возврат / отложить / перенаправить
```

Смысл состояний:

- `waiting` — талон находится в очереди;
- `called` — система назначила талон оператору, табло пригласило клиента, рабочее место зарезервировано;
- `serving` — клиент подошёл, оператор нажал «Начать обслуживание»;
- `finished` — этап обслуживания завершён или клиент перенаправлен;
- существующие сценарии `deferred` и отмены сохраняются.

Необходимо разделить времена:

- `called_at` — фактический момент объявления на табло;
- `service_started_at` — фактический момент нажатия «Начать обслуживание»;
- `finished_at` — завершение этапа;
- `last_recalled_at` — последний повторный вызов.

Предпочтительное имя нового поля — `service_started_at`: оно понятно сочетается с `called_at` и `finished_at`.

## Целевой сценарий

1. После освобождения рабочего места сервер фиксирует, когда оператор снова доступен для назначения.
2. Сервер запускает задержку, например 10–30 секунд.
3. По истечении задержки система транзакционно выбирает подходящий талон.
4. В одной транзакции талон переводится в `called`, закрепляется за оператором и окном, получает `called_at` и резервирует рабочее место.
5. Только после успешного commit сервер отправляет событие табло и интерфейсу оператора.
6. Клиент подходит, оператор нажимает одну прямую кнопку «Начать обслуживание».
7. Сервер выполняет переход `called → serving` и записывает `service_started_at`.
8. После этого оператору доступны завершение, перенаправление и остальные рабочие действия.

Оператору можно показывать обратный отсчёт «Следующий клиент через N секунд», но не следует заранее назначать конкретный талон. Раннее бронирование создаст лишнее состояние, которое придётся отменять при уходе на перерыв, закрытии окна или изменении очереди. Талон лучше выбирать непосредственно в момент системного вызова.

## Что уже можно переиспользовать

В проекте уже есть большая часть безопасного механизма назначения:

- серверная функция `claim_next_ticket()`;
- блокировка талона через `FOR UPDATE SKIP LOCKED`;
- транзакционная блокировка рабочего окна;
- защита от двух текущих талонов на одном окне;
- выбор по услугам, приоритетам и целевым окнам;
- балансировка между свободными операторами;
- WebSocket-события для табло;
- существующий паттерн фонового server worker.

Основные точки текущей реализации:

- `app/services/tickets.py` — выбор, назначение и переходы талонов;
- `app/routers/tickets.py` — HTTP endpoints;
- `app/models.py` — модель талона;
- `queue/js/operator.js` — клиентский таймер текущего автовызова;
- `data/statistics.json` — отчёты, использующие старую семантику `called_at`.

## Серверный диспетчер

На первом этапе не нужны Redis, Celery, RabbitMQ или отдельный микросервис. Для текущего масштаба это добавит инфраструктуру, но не даст полезного продуктового преимущества.

Достаточно фонового диспетчера внутри приложения и PostgreSQL как координатора:

1. Worker просыпается раз в 1–2 секунды.
2. Находит онлайн-операторов со свободным рабочим местом, для которых наступило время автовызова.
3. Использует PostgreSQL advisory lock, чтобы при нескольких экземплярах приложения диспетчер фактически выполнялся только одним.
4. Для каждого подходящего рабочего места вызывает существующий транзакционный механизм назначения.
5. После commit отправляет события интерфейсам и табло.
6. Периодическая проверка одновременно служит восстановлением после перезапуска.

Следующий серверный дедлайн следует хранить в базе. Рабочий вариант:

```text
operators.next_auto_call_at
```

Поле обновляется после освобождения рабочего места: завершения, отмены, возврата в очередь, перенаправления, отложения, а также при переходе оператора в Online.

Отдельные отложенные задачи на каждый талон не нужны: их сложнее отменять и восстанавливать после перезапуска.

## Начало обслуживания и интерфейс оператора

Когда назначен талон со статусом `called`, главным действием становится одна кнопка «Начать обслуживание». Для двух состояний не нужен dropdown или дополнительная панель.

До начала обслуживания допустимы:

- «Начать обслуживание»;
- «Повторить вызов» с существующим cooldown;
- «Не явился» или существующая отмена с обязательной причиной;
- возврат или отложение, если эти действия остаются допустимыми по бизнес-правилам.

После перехода в `serving` доступны действия фактического обслуживания: завершение, перенаправление, отложение и другие предусмотренные операции.

## Миграция исторических данных

Не следует безусловно заполнять исторические записи формулой:

```text
service_started_at = called_at + 30 секунд
```

Это будет оценка, выданная за фактическое время, и она исказит статистику.

Предпочтительный вариант:

1. Добавить nullable-поле `service_started_at`.
2. Для старых записей оставить `NULL`.
3. Зафиксировать дату перехода на новую модель.
4. Для совместимых старых отчётов временно использовать `COALESCE(service_started_at, called_at)`.
5. Новые точные KPI считать по талонам после даты перехода.

Если бизнесу обязательно нужна непрерывная ретроспективная статистика, разрешается оценочное заполнение `called_at + 30 секунд`, но такие строки должны иметь явный признак, например `service_started_at_estimated = true`.

## Новая семантика статистики

После разделения времён можно считать три честных интервала:

- ожидание в очереди: `called_at - created_at`;
- время подхода клиента: `service_started_at - called_at`;
- чистое обслуживание: `finished_at - service_started_at`.

Сейчас обслуживание считается как `finished_at - called_at`, поэтому дорога клиента к окну смешана с фактической работой оператора. Все соответствующие запросы Grafana необходимо проверить и перевести на новую семантику.

## Аварийные и пограничные сценарии

До включения системного автовызова нужно определить и протестировать:

- клиент не подошёл;
- оператор ушёл на перерыв во время обратного отсчёта;
- оператор ушёл на перерыв после вызова;
- браузер или окно потеряли соединение;
- приложение перезапустилось;
- оператор обновил страницу при уже вызванном талоне;
- два экземпляра backend одновременно запустили диспетчер;
- табло не получило событие.

Разумные правила первого релиза:

- повторный вызов остаётся ручным действием оператора;
- после повторного вызова оператор может оформить неявку или отмену;
- автоматическую отмену по таймауту пока не вводить;
- назначение хранится на сервере и восстанавливается через `/tickets/current` после обновления страницы;
- перед назначением проверять действующий статус Online, доступность окна и отсутствие текущего талона;
- потеря WebSocket-события не должна менять состояние базы, а интерфейсы должны уметь восстановиться из серверного состояния.

## Декомпозиция кода

`app/routers/tickets.py` уже превышает 1 000 строк и объединяет выбор, вызов, завершение, отмену, перенос, возврат, восстановление и побочные WebSocket-эффекты. Добавлять туда системный диспетчер нельзя.

При реализации следует вынести новые области ответственности, например:

```text
app/services/ticket_lifecycle.py
app/services/auto_dispatch.py
```

Router должен остаться тонким HTTP-слоем. Связную транзакционную логику назначения из `app/services/tickets.py` можно переиспользовать, а затем постепенно перенести без механического дробления.

## Предлагаемый порядок внедрения

1. Зафиксировать таблицу допустимых переходов состояний и действий оператора.
2. Добавить `serving` и nullable `service_started_at`.
3. Добавить серверный endpoint «Начать обслуживание» с транзакционной проверкой текущего состояния.
4. Разделить интерфейс `called` и `serving`.
5. Добавить `next_auto_call_at` и обновлять его во всех сценариях освобождения рабочего места.
6. Реализовать серверный диспетчер с advisory lock и переиспользованием `claim_next_ticket()`.
7. Удалить клиентскую ответственность за запуск автовызова, оставив браузеру только отображение серверного дедлайна.
8. Обновить восстановление текущего состояния после перезагрузки и потери соединения.
9. Перевести статистику на `service_started_at` с совместимым режимом для старых данных.
10. Покрыть транзакционные гонки, перезапуск и пограничные сценарии тестами.
11. Включать системный автовызов через feature flag и сначала проверить на одном рабочем месте.
12. После стабилизации оставить ручной вызов как административный fallback, а не основной workflow.

## Критерии готовности

- следующий клиент вызывается без действия и без открытого таймера в браузере оператора;
- один талон не может быть назначен двум операторам;
- одно рабочее место не может получить два активных талона;
- перезапуск backend не теряет и не дублирует назначение;
- оператор после обновления страницы видит текущий вызванный или обслуживаемый талон;
- `service_started_at` ставится только фактическим действием «Начать обслуживание»;
- табло получает вызов только после успешного сохранения назначения;
- отчёты отдельно показывают ожидание, подход и чистое обслуживание;
- ручной fallback не ломает системное распределение.
